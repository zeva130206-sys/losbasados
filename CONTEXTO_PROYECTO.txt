MIGRACIÓN DE MULTIMEDIA, AUTENTICACIÓN Y ADS (26 OCT 2026)
- Las imágenes se comprimen y guardan como data URLs en Firebase Realtime
  Database (máximo 1 MB por archivo); los videos pasan por `server/media-api.js`,
  que valida ID tokens Firebase Auth con correo verificado, restringe los
  scopes `hero`/`ads` a moderadores configurados en el servidor y crea archivos
  en `public/assets/uploads/<scope>/` usando GitHub Contents API. No guardar el
  token GitHub en el frontend.
- Configurar el servicio desde `.env.media-api.example`: `GITHUB_TOKEN`
  (fine-grained, Contents: write), `GITHUB_OWNER`, `GITHUB_REPO`,
  `GITHUB_BRANCH`, `PUBLIC_SITE_URL`, `FIREBASE_API_KEY`, `MODERATOR_EMAILS` y
  `ALLOWED_ORIGINS`. Ejecutar con `npm run media-api`; definir
  `VITE_MEDIA_API_URL` en el build del sitio. El repositorio está vinculado a
  GitHub; la API todavía requiere desplegarse con secretos exclusivos del
  servidor.
- Los videos guardados en GitHub Pages son públicos, incluidos los enviados a
  chats privados: el scope `private` solo organiza los archivos y no ofrece
  control de acceso ni cifrado. No subir información sensible por este sistema.
- Las imágenes están limitadas a 1 MB; videos MP4/WebM a 24 MB y hasta 30 segundos
  (duración comprobada en el cliente); no se transcodifican videos ni se
  convierten a WebP, ya que WebP es un formato de imagen. JPEG/PNG se optimizan
  en el navegador a WebP cuando el resultado ahorra espacio; GIF/WebP se
  conservan. La API también comprueba firmas de contenido, autentica, limita
  categorías, concurrencia y frecuencia.
- El login/registro utiliza Firebase Authentication con correo/contraseña y
  verificación de email. Al iniciar sesión se enlaza por email el perfil legado
  (`usersRef`) conservando su ID y permisos; los perfiles nuevos quedan
  pendientes en `pending_auth_profiles` hasta el primer login verificado. Los
  usuarios existentes que todavía no tengan cuenta Firebase Auth deben volver
  a registrarse con el correo de su perfil anterior.
- El moderador edita el medio de hero desde el formulario de juegos. El hero
  presenta la imagen estática inicialmente y carga/reproduce el video muted y
  en loop solo al hover de ratón; al salir pausa y libera el `src`, con
  transición de opacidad desde la portada.
- El footer continúa editable desde `footer_content`. El panel incorpora la
  pestaña Ads para crear, editar, activar/desactivar y eliminar anuncios,
  definir destino, esquina y frecuencia en minutos. El anuncio flotante 9:16
  aparece después del intervalo durante la sesión, abre la ficha del juego al
  hacer clic y se cierra con un botón visible. El video solo se monta mientras
  el anuncio está abierto, se pausa al ocultar la pestaña y libera su fuente al
  desmontarse.
- Los videos de chat general, mensajes privados y comentarios se guardan en
  sus scopes GitHub (`chat`, `private`, `comments`); las imágenes se guardan
  comprimidas en Realtime Database. Las imágenes son lazy y los videos usan
  `preload=none`.
- Auditoría de memoria previa: superficies temporales del canvas y URLs de
  avatar se liberan; la música no se precarga al arrancar; el AudioContext de
  interfaz se cierra al terminar; se evita crear listeners de documento por
  cada reseña y se limita a 25 el conjunto de listeners de notificaciones DM.
- Firebase Storage no se usa; las imágenes se guardan en Realtime Database.
  `npm run build`, `npx tsc --noEmit`, `node --check
  public/assets/js/main.js` y `node --check server/media-api.js` pasaron.
  Smoke test local de `/health` y CORS permitió orígenes autorizados y rechazó
  orígenes no listados. En navegador se verificó el hero y la existencia del
  panel Ads/formulario. La subida a GitHub y los flujos con cuentas reales
  quedan pendientes de configurar el repositorio, Firebase Auth y el backend.
  No hay pruebas automatizadas configuradas en `package.json`.

RESOLUCIONES RECOMENDADAS PARA IMÁGENES
- Ficha de juego: 1200 x 1600 px, vertical 3:4; WebP o JPEG. Mantener personaje,
  título y elementos importantes centrados para que el arte pueda adaptarse sin
  recortes destructivos ni deformación.
- Tarjeta del catálogo: 1600 x 1000 px, horizontal 16:10; WebP o JPEG. Mantener
  el sujeto principal centrado porque la tarjeta recorta el contenido en hover.
- Carrusel/hero de inicio: 1920 x 1080 px, horizontal 16:9; WebP o JPEG. Dejar
  márgenes de seguridad alrededor del sujeto y comprobar el encuadre en móvil.
- Revisar especialmente el arte de Rayman Legends en el hero; ajustar posición
  por juego si es necesario.

Al terminar cambios importantes, actualizar este archivo con el estado nuevo,
el punto donde quedó el trabajo y cualquier recomendación vigente de imágenes.

INTEGRACION DE MISIONES DE COMUNIDAD
- `src/CommunityMissions.tsx` está integrado debajo del chat y las solicitudes
  en la vista Comunidad. Los moderadores crean misiones ligadas al catálogo,
  configuran captura o video como evidencia requerida y revisan los envíos.
- Misiones, envíos, EXP e insignias usan Firebase Realtime Database en
  `community_missions`; la API emplea ETags para impedir recompensas duplicadas
  por revisiones concurrentes. Moderación se valida en el servidor con
  `MODERATOR_EMAILS`; el nombre/UID de quien envía se obtiene del token Firebase.
- Las capturas grandes se comprimen a WebP antes de subir (máximo 1 MB). Video
  MP4/WebM: 24 MB y 30 segundos, con duración comprobada en el cliente y tamaño
  y firma comprobados por la API.
- Las insignias aprobadas aparecen en la clasificación y en las reseñas nuevas
  asociadas a un UID Firebase; las reseñas antiguas no contienen UID y no se
  pueden asociar de forma fiable.
- El diseño de misiones ahora usa los tokens globales del tema: tarjetas con
  portadas, formulario de moderación, muro público por misión y recompensas;
  revisado para tema claro/oscuro.
- Las rutas de detalle son `#/community/missions/<id>` y la galería pública se
  obtiene desde `/api/missions/:id/submissions`. Evidencias rechazadas dejan de
  mostrarse; las pendientes se identifican como en revisión.
- Moderadores cargan el visual de portada mediante el scope seguro
  `mission-cover`; el backend comprueba rol, firma, tamaño y origen antes de
  aceptar una misión con su portada.
- Render necesita `FIREBASE_SERVICE_ACCOUNT_EMAIL` y
  `FIREBASE_SERVICE_ACCOUNT_PRIVATE_KEY` como variables privadas. No configurar
  Firestore ni publicar esas claves en el frontend. Ver `server/COMMUNITY_MISSIONS.md`.
